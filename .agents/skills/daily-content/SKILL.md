# Daily content routine

Produces a batch of genuinely verifiable content, gates it, and ships it to
production. One run ≈ 10–14 new pages.

Read `AGENTS.md` first if you have not this session. Its HARD RULES are not
style preferences — content that violates them gets reverted, and the audits
will catch most violations before you can ship anyway.

## The shape of the work

`/how-long/*` is the SEO engine (AGENTS.md §1), so **datasheets are the default
lane**, not recipes. Recipes are capped at 150 by HR-5 and are individually
authored only — never generated by looping protein × appliance (HR-1).

## Step 1 — survey

```bash
node scripts/content-gaps.mjs
```

This is deterministic and invents nothing; it reports where coverage is missing
and ranks it. Work the lanes top-down:

1. **Thin appliances** — the cheapest real wins. `dutch-oven` currently has zero
   datasheets while `oven` has 34.
2. **Cross-appliance coverage** — foods documented on only one appliance. The
   comparison query ("how long to cook X in an air fryer *vs* oven") is high
   volume and nearly unserved here.
3. **Internal links** — datasheets with no `relatedRecipeSlug`. No new prose,
   pure link equity. Cheap; do a few every run.
4. **Recipes** — only while `content/recipes/*.ts` is under 150.

## Step 2 — pick the batch

Aim for **8–12 datasheets** plus **3–5 link closures** per run. Prefer one
appliance per run so the batch shares a research context and the entries can be
cross-checked against each other.

Two filters before anything gets written:

- **Would a person actually cook this?** (HR-3) No smoked Greek yogurt, no air
  fryer cottage cheese. If you cannot picture it, drop it.
- **Can you source the numbers?** If not, drop it. A gap left open is fine; a
  fabricated number is not.

## Step 3 — author

Add entries to `data/cook-times.ts`. IDs are `CT-<PREFIX>-NNN`, zero-padded to
three, continuing from the highest existing number for that appliance:

| appliance | prefix | | appliance | prefix |
|---|---|---|---|---|
| air-fryer | `CT-AF` | | grill | `CT-GR` |
| oven | `CT-OV` | | slow-cooker | `CT-SC` |
| instant-pot | `CT-IP` | | smoker | `CT-SM` |
| boiling | `CT-BL` | | cast-iron | `CT-CI` |
| skillet | `CT-SK` | | sheet-pan | `CT-SP` |
| dutch-oven | `CT-DO` *(new — none exist yet)* | | | |

### The sourcing rule — this is the whole point

Every temperature and time carries a `verificationBasis`, and it must name a
real source. The site's defensibility rests entirely on this being true; it is
modelled on BradyBNumbers, which ranked because its datasheets were *verified*,
not because there were a lot of them.

Acceptable bases, roughly in order of strength:

- **USDA FSIS** for any safe-minimum internal temperature. Non-negotiable for
  poultry (165°F), ground meat (160°F), pork/whole cuts (145°F).
- **A named manufacturer cooking chart** — "Ninja Foodi AF100 Series Cooking
  Chart", "Instant Vortex Plus Technical Guide". Name the model.
- **Named tested hardware** — only if the run genuinely happened. Match the
  existing style: "tested 6.5 lb bone-in breast in GE Profile 30\" convection
  oven with ThermoWorks Thermapen One".

Never derive a number from an array index, a counter, a formula, or a
neighbouring entry (HR-2). If a field cannot be sourced, **omit it** — the type
allows it for `internalTempTargetF` / `internalTempTargetFormatted`, which is
exactly how boiled vegetables and starches are handled, since you fork-test
those rather than probe them.

Conventions the render layer already depends on:

- `flipAtMinutes: 0` means "no flip". Every render site tests `> 0`. Never `null`.
- `state` is one of `fresh | frozen | refrigerated | dry`, lowercase.
- A pull temperature below the USDA minimum is allowed **only** with documented
  carryover: `restMinutes >= 10` and a formatted target naming the final safe
  temp, e.g. `'160°F (pull) → 165°F (after 15-min rest)'`. The audit enforces
  this; a bare `160°F` fails.

### Prose must be unique (HR-4)

`donenessCue` and `proTip` are per-entry and must not be paraphrases of each
other across entries — duplicated prose becomes duplicated meta descriptions.
Write the actual failure mode for that specific food. The reason someone
searches "how long to cook X" is almost always that they ruined it once.

### Recipes, if the batch includes any

Only while under 150. One typed file per recipe in `content/recipes/`
(HR-11 — never hand-edit `data/recipes.json`, it is generated). IDs continue
from `0118`, zero-padded to four. `content/recipe-queue.mjs` holds vetted,
unbuilt candidates with the search intent that justifies each one.

Both content modes must be in the server-rendered HTML (HR-6) — the recipe
template already handles this; do not introduce `{mode === 'quick' && ...}`.

## Step 4 — ship

```bash
./scripts/ship-content.sh "feat(content): add 10 dutch-oven datasheets"
```

Runs every gate cheapest-first — `build:content`, `validate:recipes`,
`audit:content`, `next build`, `audit:seo` — and only commits and pushes if all
five pass. Use `--check` to run the gates without committing.

Production deploys from the **`cooking`** remote, not `origin`. Pushing to
`origin` alone builds nothing. The script pushes both, deploy remote first.

If a gate fails, fix the content — do not weaken the gate to get past it. The
one exception is a gate that is provably wrong about correct data, and then you
fix the rule *and* prove it still catches the real violation with a seeded
break, the way the poultry carryover rule was done.

## Verify the deploy

```bash
gh api repos/langtonac300/cooking-repo/deployments --jq '.[0].id' \
  | xargs -I{} gh api repos/langtonac300/cooking-repo/deployments/{}/statuses \
  --jq '.[0] | "\(.state)  \(.environment_url)"'
```

`state` goes `pending` → `success`. A `failure` means production is red: fix it
before the next batch, since content stacked on a red deploy never ships.

## Report back

State plainly: what was added, which gates ran, and the deploy state. If you
dropped a planned item because you could not source it, say so — that is a
success, not a gap in the work.

## Do not

- Generate recipes combinatorially, or raise the 150 ceiling without Alex's
  sign-off (HR-1, HR-5).
- Invent a cook time, temperature, or nutrition value (HR-2).
- Add a `Category` or `Appliance` to the unions without escalating (AGENTS.md §7).
- Hand-edit `data/recipes.json` (HR-11).
- Push without the gates, or force-push over a deploy branch that moved ahead.
